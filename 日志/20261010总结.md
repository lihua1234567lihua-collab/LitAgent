### 今天完成的东西

最开始你的 RAG 还是：

```
论文
→ Chunk
→ 每次启动重新 Embedding
→ 检索
→ LLM
```

今天我们把它逐步改成了：

```
                   Router
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
 direct_answer    local_rag    paper_search
      │              │             │
     LLM        Query Rewrite      Agent
                     ↓             ↓
                  Chroma          Tool
                     ↓             ↓
                 Reranker         LLM
                     ↓
                    LLM
```

其中最重要的几个进展是：

* **Chroma 持久化**
  * `build_index.py`：论文只需要提前建立一次向量索引。
  * `main.py` 查询时不再给 219 个 chunks 重做 Embedding。
  * `BAAI/bge-m3` 负责语义向量，Chroma 负责存储和近邻检索。
* **RAG 检索链跑通**
  * Chroma Top 50 粗召回。
  * `BAAI/bge-reranker-v2-m3` 精排 Top 5。
  * DeepSeek 根据 Top 5 证据生成答案。
  * 成功找到了 Cardil 论文里的：
    ```
    FindTreesCHM
    → local maximum
    → ForestCAS
    → Voronoi tessellation
    ```
* **Query Rewrite**
  * 我们发现中文原始问题直接检索效果很差。
  * 增加 `rag/query_rewriter.py`：
    ```
    用户问题
    → 改写成适合论文语义检索的英文问题
    → Chroma
    ```
  * 而且你已经实际看到：Query 改写质量会直接影响最终 RAG 答案质量。
* **Router 三路分流**
  * `direct_answer`：普通知识 → 直接 LLM。
  * `local_rag`：基于本地论文回答 → RAG。
  * `paper_search`：用户明确要搜索论文 → Agent + Tool。
* **代码开始模块化**
  * `rag/pipeline.py`：把 Query Rewrite、Chroma、Reranker、Generation 封成一个完整能力。
  * 接下来 `paper_search` 也准备封成独立 pipeline。
  * `main.py` 最终只负责路由，不再塞大量业务代码。

### 今天踩到的几个很有价值的坑

第一个是 Python 的缩进。

你原本的 RAG 代码跑出了：

```
direct_answer
→ RAG
→ paper_search
```

最后发现不是 Router 有问题，而是：

```
for ...:    ...else:
```

Python 把那个 `else` 当成了 `for...else`。

这个 bug 很值得记住：**Python 缩进直接决定控制流。**

第二个是：

> RAG 最终回答垃圾，不一定是 LLM 垃圾。

第一次错误答案真正的问题是：

```
Query 不好
↓
召回证据不好
↓
正确方法段没进入 Top 5
↓
LLM 只能根据垃圾 Context 回答
```

所以调 RAG 时应该从前往后排查：

```
Query
→ Retrieval
→ Rerank
→ Context
→ Generation
```

而不是一看到答案不好就改 Prompt。

第三个也很重要：

> Query Rewrite 不是把问题变成几个关键词。

最开始：

```
tree crown segmentation
```

还是不够好。

后来变成：

```
How is tree canopy segmentation or delineation performed in the literature?
```

正确方法段才重新进入 Top 5。

因为你现在用的是  **Embedding 语义检索** ，要保留：

```
how / what method / what algorithm
```

这种“用户到底想知道什么”的语义。

### 你现在已经真正理解的 RAG

现在再看整条链，就已经不是黑盒了：

```
用户问题
↓
Query Rewrite
把自然语言问题变成更适合检索的问题

↓
bge-m3
把 Query 转成语义向量

↓
Chroma
从已经保存好的论文 Chunk 向量中找 Top 50

↓
bge-reranker-v2-m3
重新判断 Query 和每个候选 Chunk 到底有多相关

↓
Top 5 Context

↓
DeepSeek
只根据证据回答原始用户问题
```

这里四个东西的职责你现在可以明确区分：

```
bge-m3       → “语义上像不像”
Chroma       → “把向量存起来并找最近的”
Reranker     → “这些候选里到底谁最能回答问题”
DeepSeek     → “根据证据组织最终答案”
```

### 当前 Mini Agent 的阶段

目前可以标成：

```
? LLM 调用
? Tool Calling
? Router
? Markdown Chunking
? Embedding
? Chroma Vector Store
? Reranker
? Query Rewrite
? Local RAG
? RAG Pipeline

? Paper Search Pipeline
? 真正的论文搜索 Tool
? Planner
? Memory
? Sub-Agent
? 更完整的 State
```

所以你已经从最开始单纯：

```
model.invoke(...)
```

走到了一个真正有点“Agent 系统味道”的架构：

```
Routing
+ Tool
+ RAG
+ Vector Store
+ Retrieval
+ Reranking
+ Query Transformation
+ Pipeline
```

下一次继续的时候，我建议就从 **把 `paper_search` 从 `main.py` 独立出来**开始，然后把目前还是假的 `search_papers` 换成真实论文检索。完成以后，再进入 Planner，会顺很多。

今天如果只记一个核心认识，我觉得可以记这个：

> **Agent 不是一个很大的 LLM 调用，而是把“判断、检索、工具、执行、生成”等不同能力拆开，再由上层进行组织。**

这也是今天这些重构真正想让你掌握的东西。
